# Snippet source & status

Every snippet open in the extension shows where it came from and whether
it's in sync with that source:

1. **New** — created directly in the extension, no backend/local origin at all.
2. **Draft** — loaded from a website draft (local IndexedDB, see
   `react_snippet_framework/Readme.indexdb.md`).
3. **Space** — loaded from a backend space.

Draft and Space each carry a second axis — **Saved** (matches the source) or
**Modified** (edited in the extension since loading) — for five states total:
`new`, `draft-saved`, `draft-modified`, `space-saved`, `space-modified`.

## Icons

Five composite SVGs, one per state: `statusNew`, `statusDraftSaved`,
`statusDraftModified`, `statusSpaceSaved`, `statusSpaceModified` in
`side_panel.js`'s `SvgIconsFactory` (see §3 — inline in JS, not standalone
files; the extension originally shipped these as `icons/status/*.svg`, now
removed). Mirrored as actual files at
`react_snippet_framework/public/assets/img/snippet-status-*.svg` so the
website can reference them the way it already references its other icons
(`<img src>`/CSS `background-image`). Preview:
https://claude.ai/code/artifact/caf3d80d-6489-47d7-bc76-c74095fd68a8

Each composites two unmodified Google Material Symbols paths (same family
already used by `side_panel.js`'s `this.icons.file` and the website's
`public/assets/img/*_24dp_..._opsz24.svg` files, so this doesn't introduce a
third icon style):

| State | Base glyph | Badge glyph | Badge color |
|---|---|---|---|
| `new` | `description` (file) | `fiber_new` | purple `#7c3aed` |
| `draft-saved` | `description` (file) | `check_circle` (check only) | green `#22c55e` |
| `draft-modified` | `description` (file) | `edit` | orange `#f97316` |
| `space-saved` | `cloud` | `check_circle` (check only) | green `#22c55e` |
| `space-modified` | `cloud` | `edit` | orange `#f97316` |

File = draft (local), cloud = space (backend) — badge sits bottom-right
(top-right for the New pill), each with a white halo so it reads over the
base glyph. Built as nested `<svg>` viewports (each sub-icon keeps its own
unmodified `viewBox="0 -960 960 960"`) rather than hand-computed path
transforms, so the exact, verified Material Symbols path data didn't need
manual coordinate math.

## 1. Data model

Every extension snippet (`chrome.storage.sync` `snippets` array entry)
carries a `source` object, set once and never re-derived from a note-count
comparison:

```js
{
  ...existing fields (id, activeNote, ...),
  source: {
    type: "new" | "space",  // "new": born in the extension, no origin at all. Everything loaded via loadSnippet is "space" -- see below, "draft" is a value of `space`, not a second `type`.
    space: "" | "draft" | "<real space name>",
    version: 0 | number,     // the backend node's version at load time (space only -- meaningless for drafts, single-user local storage has no concurrent writer)
    snippetUID: "" | string, // the original draft/space snippet's own id at its source
    isModified: boolean,     // explicit flag -- true for "new" (always needs saving) and for anything edited since load; false right after loading
  },
}
```

No separate `backId` -- an earlier iteration of this design minted one
fresh at load time to sidestep a real problem (a draft id and a space
snippet's id are generated by the same client-side scheme on the website,
so they aren't guaranteed disjoint), but `id` (below) already is a fresh,
extension-assigned value that never collides with anything, so a second
field doing the same job was redundant. `source.snippetUID` is where the
*original* source id actually lives, always paired with `source.space` so
it's unambiguous which draft/space it addresses -- that pairing, not `id`,
is what a save/update should resolve against.

Also dropped: `state` (`"new"`/`"play"`, previously set by
`createNewSnippet` and the website's `loadSnippet` default) was stored but
never read anywhere in the extension -- `source.type`/`source.isModified`
already say everything it was trying to.

**Why `version` matters.** The backend already has a real, working
`nodes.version`/`snippets.version` column (bumped on every
`PATCH /api/snippets/:id`) that nothing previously read. Capturing it here
is what would make a real optimistic-concurrency check possible later
(compare against the current backend version before saving back) --- not
wired up yet (see §4), but the data is now captured at the one point it's
cheaply available (the listing node already carries it).

**Modified detection is explicit, not derived.** `source.isModified` is
flipped to `true` directly by `background.js`'s `markSnippetModified`
helper the first time a note is added/edited/removed after loading (see
§2) -- not inferred by comparing a live note count against a snapshot. That
avoids the earlier version of this design's gap: a count-only comparison
can't tell "edited an existing note's text without adding/removing one"
from "untouched."

## 2. Where `source` gets set

**Brand new** (`side_panel.js`'s `createNewSnippet`) sets
`source: { type: "new", space: "", version: 0, snippetUID: "", isModified: true }`
directly.

**Loaded from the website** -- `content_snippetor.js`'s
`snippetAPI.loadSnippet` assigns the local `id` and builds `source` from
what the website sends:

```js
sdata.id = Date.now();
sdata.source = {
  type: "space",
  space: event.data.source.space,           // "draft" or the real space name
  version: event.data.source.version || 0,
  snippetUID: String(event.data.source.snippetUID ?? ""),
  isModified: false,
};
```

The website side (`SnippetExtensionContext.tsx`'s `loadSnippet`) takes a
`SnippetLoadSource = { space, version?, snippetUID }` third argument, and
**resolves with `{ id }`** instead of `true` -- the caller gets the
assigned id immediately, without waiting on the
`chrome.storage.onChanged` → `snippetAPI.listener` round trip (which still
independently refreshes "Opened in extension" on its own).

Call sites:

- `SnippetContainerComponent.tsx`'s `handleSnippetClick` `'play'` branch and
  `editSnippetPreview` both compute a shared `sourceSpaceLabel`: `'draft'`
  for `mode === 'drafts'`, otherwise the real `spaceName` (falling back to
  the first path segment for the generic, non-space-named `:folder` route).
- `DashboardWorkingSnippetsComponent.tsx`'s `playSnippet` reads
  `activeSnippet.source` (stamped into `activeSnippet` by `showSnippetNotes`,
  either carried from the extension's own record or from
  `editSnippetPreview`'s stamp) and forwards its `space`/`version`/
  `snippetUID` straight through.

**`markSnippetModified`** (`background.js`) is the one write path for
`isModified`: called from the `saveNote`/`updateNote`/`removeNote` message
handlers after their storage write succeeds. No-ops if the snippet has no
`source` or is already marked modified, so it's safe to call unconditionally
on every note mutation.

## 3. UI wiring

**Extension (`side_panel.js`)** -- `deriveSnippetStatus(snippet)` reads
`source.type`/`source.space`/`source.isModified` directly (no note-count
lookup); `uiUpdateSnippetList` renders `SNIPPET_STATUS_META[status].icon`
(inline SVG markup, straight into the row's `innerHTML`) as the row icon,
replacing the old `colorPalette` background-color cycling and dot/label
status line. `SnippetsListDataProvider`'s
`noteCounts`/`loadNoteCounts`/`getNoteCount` machinery (which only ever
existed to feed the old count-based status check) was removed as dead code;
its `chrome.storage.onChanged` listener now just reacts to `snippets`
changes directly, which is exactly what fires after `markSnippetModified`
writes.

**`SvgIconsFactory`** (top of `side_panel.js`) is the single place every
inline SVG icon the side panel uses lives -- the 5 status icons above, plus
what used to be three separate, partially-duplicated `this.icons = {...}`
object literals in `SnippetsListView` (open/trash/close) and `NotesView`
(edit/cancel/done/collapse/remove/branch icons; `SnippetsListView`'s
`close` and `NotesView`'s `closeIcon` were the same glyph under two names --
now one `close` entry). A single `const svgIcons = new SvgIconsFactory()`
instance is shared; both views just do `this.icons = svgIcons.icons`
rather than redefining their own subset. `content.js` (the GitHub/Chromium
Code Search note editor) keeps its own separate `strings` icon object --
it's a different content script injected into third-party pages, not
`side_panel.html`, so it can't reach this class without its own `<script>`
wiring; out of scope here.

**Website (`DashboardWorkingSnippetsComponent.tsx`)** -- a TS port of the
same `deriveSnippetStatus`, kept in sync by hand (the two codebases don't
share a build). "Opened in extension" renders
`` dw-icon-status-${deriveSnippetStatus(snippet)} `` (background-image
classes in `DashboardWorkingSnippetsComponent.less`, same convention as the
existing `.dw-icon-*` classes) instead of a static `dw-icon-new`.

## 4. Known gap — Space can't get back to "Saved" today

Unchanged from before: "Save" (`onSaveWithPath` → `MoveDialogComponent`) is
still a stub -- nothing calls `userDataTreeService.updateSnippet`. Only
"Save as draft" persists for real. A `space-modified` snippet's only real
way out today is "Save as draft" (which reclassifies it as a new
`draft-saved` draft and removes it from the extension), not "save back to
the space it came from." `source.version` is captured specifically so a
real "save to space" implementation can do an optimistic-concurrency check
when this gets built -- not wired up yet.

## Related — "Active snippets" / "Recently watched" no longer mirror the extension

Two decisions made alongside this design, implemented in
`LocalSnippetsStoreContext.tsx`/`DashboardWorkingSnippetsComponent.tsx`:

- **`activeSnippets`** (the website's IndexedDB) never gets a record for a
  snippet opened via "Opened in extension" -- only for snippets opened
  directly on the site (the "Active snippets" aside, or a space/draft's
  "Edit" action). The `isLocal` flag that used to filter this table for
  display is gone; the table is local-only by construction now, since the
  extension is fully self-describing via `source` and doesn't need a
  website-side lookup record to save back -- a website-IndexedDB pointer
  would break if that record were ever cleared, which IndexedDB doesn't
  durably protect against the way this design does.
- **`recentlyWatched`** no longer gets a new entry on every open/preview --
  only on save (`onSaveAsDraft`, always creates-or-refreshes) and close
  (`closeActiveSnippet`, refreshes an *existing* entry only, never creates
  one). Each record now carries its own `isLocal` (opened directly on the
  site vs. via the extension), read back when the record is later
  re-clicked so reopening it doesn't misclassify its origin. A
  `removeRecentlyWatched(id)` store method exists for when "remove" itself
  becomes a real action (`handleSnippetClick`'s `'remove'` branch is still
  a no-op everywhere) -- not wired to anything yet.
